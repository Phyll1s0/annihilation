# GRAY 关卡编写与认证

关卡集中放在 `data/levels.json`。每关使用固定宽度的字符串数组表示地形，另保存模式共用的标题和教学文案。

## 地图字符

| 字符 | 含义 |
| --- | --- |
| `#` | 没有地板，不能进入 |
| `.` | 普通空地板 |
| `w` | 普通地板上的白棋子 |
| `b` | 普通地板上的黑棋子 |
| `A`～`Z` | 传送门组，每个用到的字母必须恰好出现两次；当前主线主要使用 A、B |

`tokens` 可选，用 `[格子编号, 颜色]` 将棋子放在传送门或普通空格上。颜色 `1` 是白，`-1` 是黑。格子编号从 0 开始，按行排列，等于 `y * 地图宽度 + x`。不能覆盖已有棋子或缺失地板。

```json
{
  "id": "example",
  "title": "隔空相遇",
  "chapter": "另一端",
  "description": "进入传送门，与另一端的黑棋子合并。",
  "layout": ["wA#A"],
  "tokens": [[3, -1]]
}
```

## 制作流程

1. 编写布局，保证每行等宽、黑白数量相等、每组传送门有两个端点。
2. 运行 `python3 tools/certify_levels.py --write`。
3. 工具补全 `optimal_moves`、`solution` 和 `proof`。不可解或超过搜索上限时失败，不能将目标步数当作已验证结果。
4. 运行 Godot 规则测试，交叉验证最优步数并重放每关保存的解。
5. 进入游戏分别测试自由通关和最少步数目标，观察死局、撤销和传送的反馈。

```bash
python3 tools/certify_levels.py
godot --headless --path . --script tests/run_tests.gd
```

`solution` 每步包含源格子 `source` 与方向 `up/right/down/left`。这是制作与验证数据，游戏界面不会直接显示答案。`proof.visited` 是 Python BFS 找到最短解时已发现的状态数，不是难度评分。

存档以 `id` 与谜题内容哈希关联。布局、棋子、规则版本或最优步数变化后，旧通关记录不会用于新布局；只改标题或教学文案可以保留进度。`data/legacy_v1.json` 是首版 12 关的固定迁移映射，不应随新关卡重新生成。

## 新增关卡的设计重点

| 关卡 | 最少步数 | 推理重点 |
| --- | --- | --- |
| 13 两段路 | 6 | 先分区配对，避免消融切断剩余路线 |
| 14 三次相遇 | 10 | 三对棋子共用窄口，决定相遇顺序 |
| 15 借一步 | 6 | 同色借位，为另一颗棋子让出位置 |
| 16 桥两端 | 8 | 留住唯一连接，选择合并地点 |
| 17 先过门 | 10 | 在狭窄空间中安排传送与出口疏通 |
| 18 留一扇门 | 4 | 先消除一端，再踏上退化的另一端 |
| 19 双向来信 | 10 | 两组门连接不同区域，安排跨区配对 |
| 20 让出出口 | 8 | 出口初始同色阻挡，先移动出口棋子，再安排绕行 |

这些重点用于制作和试玩评估，玩家界面只显示必要的引导。关卡不是单纯按步数排序：新机制的第一关可以更短，之后再组合多个约束。
